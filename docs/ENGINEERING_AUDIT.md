## 文档必须保持的事实

- 简单确定性本地任务可跳过模型工具规划；复杂任务调用角色配置中的规划/工具职责模型，选择取决于实际能力配置和 fallback。
- AgentService 的 plan 阶段不由执行门控管理；execute 才进入 RuntimeTaskRegistry。
- 锁范围是任务类型和会话的组合，不同类型同会话不等同互斥。
- 启动时将遗留任务标 interrupted，不会自动重放工具；不是完整断点恢复。
- GoalVerifier 是确定性工具结果启发式检查，不是完备的语义目标验证。
- 未知 Tool Calling 能力允许尝试；没有工具选择不能证明服务不支持 Tool Calling。
- 旧 always 授权资料用于归档；当前权限按模式、风险和当前任务授权决定。

## 后续 0.1.2：记事本窗口问题

2026-10-15 按用户审核意见单独排查。发现用户请求的 GUI 应用被传入 `windowsHide:true`；libuv 在 Windows 上会将该选项映射为 GUI 的 SW_HIDE，说明见 [上游实现](https://github.com/libuv/libuv/blob/v1.52.0/src/win/process.c)。早期对照中改为 false 后曾成功，但后台应用扫描同时完成，存在身份记录变化，不能据此声称单一标志就完全解决了问题。

首次 0.1.2 安装测试仍返回 APP_NOT_READY，进一步确认：现代记事本的发现记录仅有准确 AUMID、没有 EXE 路径时，内置应用解析忽略了该记录并回退系统入口，导致后续观察丢失身份。修复以准确的已登记 AUMID 关联内置记事本，保留传统 EXE 和自定义入口优先级，不放宽为仅按进程名或任意后代匹配。

0.1.2 同时调整用户请求打开的 GUI 启动标志，后台 worker/后端仍隐藏运行；授权、窗口归属和未就绪失败判断保持不变。启动回归覆盖参数、创建失败、真实窗口就绪、取消及准确应用身份，默认 Electron 回归为 11 组。受控安装测试通过 `-RunUI -StartNotepad` 显式验证真实记事本可用窗口和聚焦；最终产物的安装结果单独记录。原失败记录保留为历史证据，不代表所有客户端启动问题均已解决。

修复后的本地 0.1.2 安装包已实际完成 28 项界面检查，包括通过已登记的 AppsFolder 入口启动记事本、核验窗口可见/响应和聚焦、Chat/Work、工作台、网页隔离、重启和正常后端退出。测试后的卸载及原注册信息/快捷方式恢复均通过，未调用外部模型或语音。此证据来自本机安装验收，最终 tag 云端产物仍需下载后再次安装核对。
